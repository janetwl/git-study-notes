**ADR 自学包 · 从理解到会写**(2026-11-05,书单 + 文献 + 模板 + 示例 + 练习)

先说实情:ADR 这个题目**没有专著**——它源自 Michael Nygard 2011 年的一篇博客([Documenting Architecture Decisions](https://www.cognitect.com/blog/2011/11/15/documenting-architecture-decisions)),靠 [Martin Fowler 的百科页](https://martinfowler.com/bliki/ArchitectureDecisionRecord.html) 和 [adr.github.io](https://adr.github.io/) 社区推广开来。所以这个包按三层给你材料:先建立心智模型(读 10 分钟就够),再抄模板开写(今天就能写第一条),最后才是书(把"决策"当认知框架读透)。

---

**▍1 · 心智模型:ADR 到底在记什么**

一句话:在**做决策的当时**,用一页纸把"为什么这么选"钉死——因为半年后没人记得背景,包括你自己。

一条典型 ADR 只有五件事:

- **标题**:动词开头,一句话说清决定("001. 用 PostgreSQL 存订单数据")
- **状态**:提议 / 已接受 / 已弃用 / 被 007 取代
- **背景**:当时面临什么处境、什么约束、掌握了(和没掌握)什么信息
- **决策**:选了什么,关键理由
- **后果**:带来了什么好处,**付出了什么代价、引入了什么风险**(这一栏最常被偷懒,也最值钱)

两个最关键的认知点:

1. **ADR 记的是"决策当时的推理",不是"事后证明对不对"。** 一条 ADR 即使今天看选错了,只要当时推理成立,它就是好记录。正确姿势是:写一条新的取代它,把旧的标记"被取代"——**永不修改原文**。这条"不可变 + 取代链"的设计,就是它对抗后见之明偏差的机制。这也是它和 changelog、wiki 的本质区别。
2. **价值不在文档,在"逼出隐含假设"。** 写"背景"和"后果"时,团队里没说出口的顾虑会被逼上纸面。你老师叫它"认知框架"就是这个意思:它是**思维纪律**,不是文档模板。

**▍3 · 模板:直接抄,别自创**

**Nygard 极简版**(推荐起步,30 行写完一条):

```markdown
# NNN. 标题(动词开头,一句话说清决定)

日期: YYYY-MM-DD
状态: 提议 | 已接受 | 被 NNN 取代

## 背景
当时面临什么问题?有哪些约束(时间/技术/团队/成本)?

## 决策
我们选择了 X,因为 A、B、C。
考虑过的选项:Y(放弃,因为…)、Z(放弃,因为…)

## 后果
好的:…
坏的/代价:…
风险与待观察:…
```

**MADR 结构化版**(需要方案对比表时用):[adr/madr](https://adr.github.io/madr/),多"选项对比、论证要点、未决问题"几栏。个人用先不必,极简版够用。

存放约定:仓库里 `docs/adr/`,文件名 `001-短标题.md`,编号只增不改;在 `docs/adr/README.md` 留一行索引表。命令行走想省事可用 [adr-tools](https://www.hascode.com/managing-architecture-decision-records-with-adr-tools/)。

**▍4 · 一条完整示例(拿你自己的工作区写的)**

假设 `E:\git-workspace` 里要立这条:

```markdown
# 001. 学习笔记用纯 Markdown + Git 管理,不用 Notion/语雀

日期: 2026-11-05
状态: 已接受

## 背景
课程笔记、对话存档、书籍蒸馏物持续增多,需要选一个能长期
存放、可检索、不怕平台变故的载体。约束:单人为主、偶尔
AI 工具需要直接读写文件、预算敏感。

## 决策
选择纯 Markdown 文件 + Git 仓库作为唯一事实源。
考虑过的选项:
- Notion/语雀:视图和协同强,但数据在别人手里,十年后能否
  完整导出不可知 → 放弃
- Obsidian 库不放 Git:上手快,但换机/协作即失联 → 放弃

## 后果
好的:可 grep、可 diff、迁移成本≈0,Claude Code 等 AI 工具
能直接读写全部资产。
坏的:没有数据库视图/看板/双向链接的华丽形态,复杂项目管理
要靠手写 md 表格(如课程进度看板)硬撑。
风险:图片/PDF 增大仓库,需定期把二进制走 Git LFS 或外链。
```

注意"坏的"那栏——诚实写下代价,这条 ADR 才可信。

**▍5 · 什么时候值得写(三个触发问题)**

- **改起来贵吗?**(难逆转:选数据库、定课程结构、买设备)
- **将来会有人惊讶"为什么当初这么干"?**
- **有真实备选吗?**(不是"只有一条路")

任一为"是"→ 值得 5 分钟写一条;全为"否"→ 别写,免得为记而记。日常 90% 的编码决定(变量命名、函数拆分)**不该**进 ADR——ADR 记的是"架构级"=贵、慢、难回头的事。

常见坑,四条:事后补写(推理已丢)、只记结论不记备选项(变成 changelog)、把会议辩论全文塞进去(只留决定和关键考量)、修改已接受的旧 ADR(用取代)。

**▍6 · 书单:三层各一本**

- **怎么写 + 怎么在团队推行**:[《Facilitating Software Architecture》](https://www.oreilly.com/library/view/facilitating-software-architecture/9781098151850/ch06.html) — Andrew Harmel-Law,O'Reilly 2024。目前唯一有**专门 ADR 章节**(第 6 章,链接可试读)的书。英文原版,暂无中译。
- **决策背后的权衡思维**:[《软件架构难点解惑》(*Software Architecture: The Hard Parts*)](https://m.douban.com/book/subject/36388593/) — Neal Ford 等,东南大学出版社[影印版](https://m.douban.com/book/subject/36388593/),另有[社区中文翻译](https://github.com/ArkTicketTech/software-architecture-the-hard-parts)。全书主张:**架构没有最佳实践,只有取舍**——ADR 正是把取舍固化下来的工具(见[书评](https://plainionist.github.io/Software-Architecture-The-Hard-Parts/)、[ThoughtWorks 第 7 章英文样章](https://www.thoughtworks.com/content/dam/thoughtworks/documents/books/bk_software_architecture_hard_parts_ch7_en.pdf))。
- **认知框架层(老师那句话的本意)**:《对赌》(*Thinking in Bets*)— Annie Duke。"背景→选项→后果"的本质是把**决策质量与结果质量分开**、对抗后见之明。ADR 就是工程师版"决策日志",读完你会发现这模板能记一切决定。

顺带一提:国标/国际标准 ISO/IEC/IEEE 42010 也把"架构决策 + 理由 + 后果"列为核心概念——ADR 不是网红发明,是标准思想的轻量落地。

**▍7 · 三个练习(做完第一个,你就"会用"了)**

1. **今天(30 分钟)**:把 ▍4 的示例抄进 `E:\git-workspace\docs\adr\001-....md`,背景/选项/后果改成你自己的话。
2. **本周(考古 ADR)**:挑一个你今年做过的、现在还有影响的决定(比如课程路线、模型预设计方向),用同一模板**补写**一条,状态标"已接受(事后补记)"——诚实写下"当时的信息我不全,但我当时以为是……"。你会立刻体会到"没在当场记"丢了什么。
3. **下周(跨界)**:给一个非代码决定写 ADR(3D 打印设备/复课顺序)。如果模板照样好用,说明你掌握的是框架,不是格式。
